# Football Data Sentinel

Football Data Sentinel is a validation and self-recovery layer for scraped
football data. It sits between the raw scraper output and downstream
analysis, with the goal of preventing malformed or structurally changed
source data from silently entering the analytics pipeline.

The current implementation is built around the EFL Championship 2025-26
player statistics dataset scraped from FBref. The validation and recovery
components are designed to be reusable across future football datasets and
scraper runs.

## Pipeline

The current pipeline is:

    raw JSON
        ↓
    player-row filtering
        ↓
    record validation
        ↓
    dataset validation
        ↓
    schema drift detection
        ↓
    field mapping
        ↓
    recovery + revalidation
        ↓
    status classification
        ↓
    run report

Every run produces a timestamped JSON report under `data/runs/`.

## Validation

The scraper's raw output isn't trusted by default. Every record
passes through `validation/schema.py` before being treated as
usable data.

Checks currently implemented:
- **Schema presence** — all required fields exist on the record
- **Type validation** — text fields are strings; numeric fields
  convert cleanly to a number (scraped values arrive as strings,
  so this checks convertibility, not raw Python type)
- **Range validation** — numeric fields fall within plausible
  bounds (e.g. age 15-45, minutes 0-4140 for a season)
- **Cross-field validation** — logically impossible combinations
  are flagged (e.g. starts exceeding games played)
- **Row filtering** — FBref's combined stats table includes blank
  divider rows between squads; these are filtered before
  validation runs, not treated as malformed player data
- **Dataset-level checks** — total record count is checked against
  an expected range, and each required field is checked to confirm
  it isn't empty across the entire dataset (catches a whole column
  silently disappearing, not just one bad record)

Current status: 573 raw rows scraped from the EFL Championship
2025-26 stats page, 551 valid player records after filtering,
all validation checks passing. Each check has been verified
against deliberately malformed test data to confirm it actually
detects the problem it's meant to catch, not just against clean
input.

## Drift Detection

Sentinel compares the fields present in an incoming record against
the expected schema defined in `validation/schema.py`.

Drift currently identifies:
- **Missing fields** — fields required by the schema but absent
  from the incoming record
- **Unexpected fields** — fields present in the incoming record
  that are not part of the expected schema

For example, replacing `games` with `appearances` produces:

    missing: ["games"]
    unexpected: ["appearances"]

Field mappings are generated by `validation/drift.py`. Mapping
confidence is calculated using string similarity rather than
assuming that every unexpected field is safe to rename.

## Recovery and Status

When drift is detected, Sentinel does not repair automatically.
It proposes a field mapping using string similarity, then only
applies the repair if confidence clears a threshold (0.85) and
the repaired record passes the full validation pipeline.

Known domain aliases can also be explicitly trusted where lexical
similarity is insufficient. For example, the current football
schema recognizes `appearances` → `games` as a trusted mapping
rather than lowering the general confidence threshold to make
the repair pass.

Status meanings:
- **PASS**: clean dataset, no issues requiring recovery
- **RECOVER**: drift was detected, a safe repair was applied, and
  the repaired record passed validation
- **QUARANTINE**: drift was detected but no safe repair was possible,
  either because confidence was too low or the repair itself
  still failed validation
- **FAIL**: validation errors with no recoverable drift involved
- **WARNING**: non-fatal condition requiring attention

Recovery is deliberately conservative. An uncertain mapping is
rejected rather than guessed.

A recovery attempt is not considered successful merely because a
field was renamed. `validation/recovery.py` re-runs the complete
record validation suite against the repaired record before
returning `success: true`.

## Run Reports

Each pipeline execution produces a timestamped JSON report under
`data/runs/`.

A clean run currently produces output of this form:

    {
      "status": "pass",
      "records": {
        "raw": 573,
        "valid": 551
      },
      "validation": {
        "passed": true,
        "errors": []
      },
      "drift": {
        "detected": false,
        "missing": [],
        "unexpected": []
      },
      "repair": {
        "attempted": false
      }
    }

The report records the decision made by Sentinel for that run
rather than silently overwriting the source data.

## Failure Cases Verified

The recovery path has been tested against a deliberately modified
record where:

    games → appearances

The resulting drift was correctly detected as:

    missing: ["games"]
    unexpected: ["appearances"]

The first implementation rejected this mapping because the two
field names have low lexical similarity. This exposed a limitation
in treating semantic field aliases as ordinary string similarity.

The mapping was subsequently added as an explicit trusted domain
alias. The repair then passed the complete validation suite and
was classified as `RECOVER`.

A separate dataset-level failure was also caught when the expected
record-count range was incorrectly configured as 700-850 against
the current dataset's 551 valid player rows. The range was corrected
to the observed Championship dataset boundary of 500-620 rather
than weakening the dataset validation itself.

## Running the Pipeline

From the project root:

    python pipeline.py

The current pipeline reads:

    data/sample/players_raw.json

and writes a timestamped run report to:

    data/runs/

The current output is an audit report of the pipeline decision.
The next integration step is to connect this validated pipeline
directly to the production scraper and downstream football analytics
dataset.
